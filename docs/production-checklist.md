# Production checklist

Этот чек-лист описывает полный путь деплоя Django-приложения из этого репозитория на сервер с помощью Docker Compose и GitHub Actions.

Сейчас в репозитории уже есть `Dockerfile`, `docker-compose.yml`, `.env` и `.env.example`. Текущая схема работает на SQLite в volume, а GitHub Actions workflow для деплоя еще нужно добавить.

## 1. Подготовить основу проекта

- [ ] Убедиться, что проект стабильно запускается локально.
- [ ] Прогнать тесты и убедиться, что они проходят.
- [ ] Проверить, что все настройки для production будут браться из переменных окружения или `.env`.
- [ ] Проверить, что SQLite хранится в отдельном volume и не теряется при перезапуске контейнера.
- [ ] Проверить, что статические и media-файлы можно хранить отдельно от кода.
- [ ] Обновить README под новый способ запуска через Docker Compose.

## 2. Добавить Docker-слой

- [ ] Проверить, что `Dockerfile` есть и собирает Django-приложение.
- [ ] Проверить, что `docker-compose.yml` есть и поднимает только `web`-сервис.
- [ ] Проверить, что `env_file` указывает на `.env`.
- [ ] Проверить, что volume для SQLite подключен и база хранится отдельно от кода.
- [ ] Проверить, что volume для `media` есть.
- [ ] Проверить, что volume для `staticfiles` есть.
- [ ] Если нужен reverse proxy, добавить Nginx отдельным контейнером или на хосте.

## 3. Настроить production settings

- [ ] Оставить общие настройки в `config/settings/base.py`.
- [ ] Добавить production-настройки через env-переменные.
- [ ] Задать `DEBUG=False` в production.
- [ ] Настроить `SECRET_KEY` через secret, а не хранить в репозитории.
- [ ] Задать `ALLOWED_HOSTS` для домена и IP сервера.
- [ ] Настроить `CSRF_TRUSTED_ORIGINS` для HTTPS-домена.
- [ ] Убедиться, что production использует SQLite только если это осознанный выбор для небольшого проекта.
- [ ] Настроить `STATIC_ROOT` и `MEDIA_ROOT` для контейнеров.
- [ ] Проверить, что `collectstatic` работает в production.

## 4. Подготовить сервер

- [ ] Купить VPS с Linux.
- [ ] Привязать домен к серверу через DNS A-запись.
- [ ] Установить Docker.
- [ ] Установить Docker Compose plugin.
- [ ] Открыть порты `22`, `80`, `443`.
- [ ] Создать отдельного пользователя для деплоя.
- [ ] Настроить SSH-ключи для GitHub Actions.
- [ ] Создать каталог для приложения, например `/opt/landing`.
- [ ] Подготовить `.env` на сервере.
- [ ] Не хранить секреты в репозитории.
- [ ] Убедиться, что `.env.example` отражает актуальные переменные проекта.

## 5. Организовать CI

- [ ] Создать GitHub Actions workflow для проверки кода на `push` и `pull_request`.
- [ ] Добавить установку зависимостей.
- [ ] Добавить запуск тестов.
- [ ] Добавить линт, если он используется в проекте.
- [ ] Добавить сборку Docker-образа.
- [ ] При использовании registry добавить push образа в GitHub Container Registry или Docker Hub.
- [ ] Включить кеширование сборки, чтобы ускорить pipeline.

## 6. Организовать CD с кнопкой запуска

- [ ] Создать отдельный workflow с триггером `workflow_dispatch`.
- [ ] Использовать этот workflow как кнопку ручного деплоя в GitHub Actions.
- [ ] В job деплоя подключаться по SSH к серверу.
- [ ] На сервере выполнять `docker compose pull`.
- [ ] Затем выполнять `docker compose up -d`.
- [ ] После этого запускать миграции.
- [ ] Затем собирать статику.
- [ ] После деплоя выполнять healthcheck.
- [ ] При необходимости разделить build job и deploy job.

## 7. Что должно быть в GitHub Secrets

- [ ] `SSH_HOST`.
- [ ] `SSH_USER`.
- [ ] `SSH_PRIVATE_KEY`.
- [ ] `SSH_PORT`, если порт не стандартный.
- [ ] `REGISTRY_USERNAME`, если используется registry.
- [ ] `REGISTRY_TOKEN`, если используется registry.
- [ ] `DJANGO_SECRET_KEY`.
- [ ] `DJANGO_ALLOWED_HOSTS`.
- [ ] `CSRF_TRUSTED_ORIGINS`.
- [ ] `DATABASE_URL`, если она используется в `.env`.

## 8. Что должно быть в workflow

- [ ] `checkout` репозитория.
- [ ] Настройка Docker Buildx.
- [ ] Логин в registry, если он используется.
- [ ] Сборка и публикация образа.
- [ ] SSH-подключение к серверу.
- [ ] Обновление контейнеров.
- [ ] Применение миграций.
- [ ] Сборка статики.
- [ ] Проверка, что сервис поднялся без ошибок.

## 9. Порядок первого запуска

- [ ] Сначала поднять проект локально через Docker Compose и проверить, что `.env` подхватывается.
- [ ] Проверить миграции.
- [ ] Проверить collectstatic.
- [ ] Проверить открытие главной страницы.
- [ ] Проверить админку.
- [ ] Проверить загрузку media.
- [ ] Проверить тесты в CI.
- [ ] Запустить деплой вручную через кнопку `workflow_dispatch`.
- [ ] Повторно запустить деплой и убедиться, что он идемпотентен.

## 10. После первого запуска

- [ ] Настроить резервные копии базы данных.
- [ ] Настроить резервные копии media.
- [ ] Настроить логирование контейнеров.
- [ ] Настроить restart policy для сервисов.
- [ ] Добавить мониторинг доступности сайта.
- [ ] Настроить регулярный контроль обновлений и бэкапов.

## 11. Короткая рабочая схема

1. Код пушится в GitHub.
2. GitHub Actions собирает и проверяет проект.
3. По кнопке `workflow_dispatch` запускается deploy job.
4. GitHub Actions подключается к серверу по SSH.
5. На сервере обновляются контейнеры через Docker Compose.
6. Django применяет миграции и собирает статику.
7. Сайт становится доступен на домене.

## 12. Итог

Для этого проекта правильная схема деплоя выглядит так:

- Django запускается в Docker.
- SQLite хранится в отдельном volume.
- Статика и media вынесены в volumes.
- GitHub Actions отвечает за сборку и деплой.
- Ручной запуск деплоя делается через `workflow_dispatch`.

Если нужно, следующим шагом можно сразу подготовить конкретные файлы для внедрения:

1. `Dockerfile`
2. `docker-compose.yml`
3. `.github/workflows/deploy.yml`
4. production-правки в `config/settings/base.py`
